# PPOLO 시스템 설계서

> 서비스명: **PPOLO**  
> 목적: 운동 기록과 경쟁을 결합해 운동을 더 재미있게 만드는 **기록 + 소셜 네트워크 서비스**

---

## 1. 서비스 개요

PPOLO는 사용자의 운동 활동과 신체 변화를 기록하고, 다른 사용자와 실시간 경쟁을 통해 운동의 동기부여를 높이는 서비스다.

핵심 사용 맥락은 다음과 같다.
- **모바일 앱**: 운동 기록, 대결 참여/생성, 소셜, 캘린더, 신체 정보 관리
- **스마트 워치 앱**: 활동 시작/중지 제어, 현재 페이스 확인, 운동 중 실시간 보조
- **백엔드 API**: 인증, 기록 저장, 경쟁방, 실시간 랭킹, 채팅, 알림, 통계
- **DB/분석**: 운동 데이터, 경쟁 결과, 인바디 변화, 추천 시스템 기반 데이터 축적

---

## 2. 제품 원칙

PPOLO는 다음 원칙으로 설계한다.

- **기록의 정확성**: 운동/대결 데이터는 사용자의 실제 행위와 기기 센서 데이터를 함께 저장한다.
- **실시간성**: 경쟁은 현재 시점의 거리/시간/페이스를 반영해 실시간 순위를 보여준다.
- **확장성**: 초기에는 런닝/헬스 중심으로 시작하고, 추후 다른 운동 카테고리를 추가한다.
- **플랫폼 분리**: 모바일 앱과 스마트 워치 앱은 별도 클라이언트로 분리한다.
- **도메인 분리**: 백엔드는 기능별 경계를 명확히 하고, 나중에 서비스 분리가 가능하도록 설계한다.

---

## 3. 추천 아키텍처

## 3.1 백엔드 아키텍처: 모듈러 모놀리스 우선, MSA는 단계적 도입

초기에는 **모듈러 모놀리스(modular monolith)** 를 추천한다.

이유:
- 서비스 초기에는 기능이 많아 보여도 실제 트래픽/조직 규모는 아직 작다.
- 활동 기록, 경쟁, 채팅, 알림은 서로 긴밀히 연결돼 있어 초기부터 완전한 MSA로 나누면 운영 복잡도만 커진다.
- Go는 패키지 경계와 인터페이스 분리가 명확해서 모듈러 모놀리스에 잘 맞는다.

다만, 다음 조건이 충족되면 특정 도메인부터 MSA로 분리한다.
- 팀이 기능별로 분업되기 시작할 때
- 경쟁/채팅/알림 트래픽이 급증할 때
- 실시간 처리와 배치 처리의 성격이 완전히 갈라질 때
- 독립 배포가 필요한 기능이 생길 때

### 권장 도메인 경계

- **Auth / Identity**: OAuth2 소셜 로그인, 세션/토큰, 디바이스 등록
- **User / Profile**: 사용자 기본 정보, 프로필, 공개 범위, 팔로우/차단
- **Health / Body Metrics**: 키, 몸무게, 체지방, 골격근량, 인바디 기록
- **Activity Log**: 헬스/런닝 기록, 센서 데이터, 운동 이력
- **Competition**: 경쟁방 생성/입장/진행/종료/투표
- **Ranking / Realtime**: 실시간 순위 계산, 현재 페이스/진행률 계산
- **Social / Chat**: DM, 채팅방, 메시지 송수신
- **Calendar**: 기록/대결 일정 조회
- **Notification**: 푸시, 인앱 알림, 이벤트 알림
- **Analytics / Recommendation**: 추천 데이터, 집계, 통계
- **Admin / Ops**: 운영자 기능, 신고, 제재, 이벤트 관리

## 4. 추천 기술 스택

## 4.1 API 서버

백엔드는 **Go** 로 구현한다.

권장 구성:
- **언어**: Go
- **HTTP Router**: `chi` 또는 `gin`
- **DB**: PostgreSQL
- **캐시 / PubSub**: Redis
- **실시간 이벤트**: WebSocket + Redis Pub/Sub 또는 NATS
- **비동기 작업**: Background worker / queue
- **ORM/SQL 계층**: `sqlc` + `pgx` 조합 권장
- **마이그레이션**: goose / golang-migrate
- **인증**: OAuth2 소셜 로그인 + JWT 또는 세션 토큰
- **관측성**: OpenTelemetry + 구조화 로그 + 메트릭

### MSA 추천 여부

- **초기 권장**: MSA 아님
- **권장 형태**: 모듈러 모놀리스 + 필요 시 워커 분리
- **향후 분리 후보**: 채팅, 알림, 추천/분석, 실시간 랭킹 보조 서비스

## 4.2 모바일 앱

요구사항상 **모바일 네이티브 앱** 으로 설계한다.

권장 방향:
- MVP 우선: **iOS 먼저**, Android는 이후 확장
- iOS: Swift + SwiftUI
- Android: Kotlin + Jetpack Compose

운영 전략은 두 가지다.
1. **양 플랫폼 동시 네이티브 개발**: UX 일관성이 높고 센서/헬스 연동에 유리
2. **MVP 우선 1개 플랫폼 출시 후 확장**: 초기 속도를 높일 수 있음

PPOLO는 헬스/런닝/워치 연동이 중요하므로, 장기적으로는 네이티브 분리가 적합하다.

### 모바일 내비게이션
- 하단 탭 중심 구조를 사용한다.
- 탭 구성: **Home / Training Log / Competition / Social / Calendar**
- MVP에서는 Home / Training Log / Competition을 우선 구현하고, Social / Calendar는 초기에는 제한된 콘텐츠 또는 스켈레톤 형태로 둘 수 있다.
- `Competition` 탭은 진입 규칙을 가진다.
  - 진행 중인 경쟁이 있으면 목록이 아니라 **현재 진행 중인 경쟁 화면** 으로 바로 이동한다.
  - 진행 중인 경쟁이 없을 때만 경쟁방 목록/검색/초대 화면을 보여준다.

### 홈 화면 원칙
- 홈 초기 노출은 **공지사항 + 이벤트** 위주로 구성한다.
- 빈 상태는 공통 문구 **"데이터가 존재하지 않습니다."** 를 표시한다.
- 홈은 대시보드라기보다 빠른 진입점 역할을 한다.

## 4.3 스마트 워치 앱

스마트 워치는 모바일 앱의 보조 인터페이스가 아니라 **독립 클라이언트** 로 본다.

권장 방향:
- iPhone 연동: **watchOS / Apple Watch 우선**
- Android 연동: Wear OS는 이후 확장 후보

워치의 역할:
- 운동 시작 / 일시정지 / 종료
- 현재 페이스 확인
- 최소한의 상태 확인
- 경쟁 중 실시간 상태 확인
- 센서 데이터 수집 동의 시 심박수/활동 데이터 전송

워치 UI는 정보 과부하를 피하고 상태 + 최소 버튼만 노출한다.

워치 화면 시나리오 초안은 아래 기준으로 분리한다.
- **운동기록**: 시작 / 일시정지 / 재개 / 종료만 제공하는 리모컨
- **런닝기록**: 시작 / 일시정지 / 재개 / 종료만 제공하는 리모컨
- **경쟁**: 대기실 / 준비완료 / 경쟁 중 상태 모니터링 + 최소 버튼

워치에서는 모바일보다 더 강하게 다음 원칙을 지킨다.
- 한 화면에 한 행동만 배치
- 입력은 받지 않는다
- 상세 입력/수정은 모바일로 넘긴다
- 진행 중 화면은 상태 모니터링 중심으로 구성한다

## 5. 기능 설계

## 5.1 운동 활동 기록

### 지원 우선순위
- 1차: **헬스, 런닝**
- 2차: 요가, 자전거, 필라테스, 크로스핏, 하이록스

### 헬스 기록
사용자가 모바일 앱에서 수동 입력한다.
- 운동 부위
- 운동 종목
- 무게
- 횟수
- 세트 수
- 운동 시간
- 메모

권장 추가 규칙:
- 운동 부위는 가슴 / 등 / 어깨 / 하체 / 복근 / 팔을 최소 시작점으로 둔다.
- 운동 종목은 마스터 목록 기반으로 관리한다.
- 휴식 / 메모 / RPE는 선택 입력으로 둔다.
- 헬스 기록은 여러 번 입력 가능하며, 같은 날 여러 번 기록해도 덮어쓰지 않고 각각 독립된 기록으로 저장한다.

워치는 헬스 기록의 입력 단말이 아니라 **리모컨** 으로만 사용한다.
- 워치에서는 운동 부위, 종목, 무게, 횟수, 세트 수를 입력하지 않는다.
- 워치에서는 시작 / 일시정지 / 재개 / 종료만 제공한다.
- 상세 입력은 모바일에서만 처리한다.

워치 연동 시 추가 저장 가능:
- 운동 시작 시각
- 심박수
- 활동 중 심박 변화

### 런닝 기록
런닝은 시작/중지 기반 활동 기록으로 설계한다.
- 시작
- 일시정지
- 재개
- 종료

기록 항목:
- 심박수
- 케이던스
- 페이스
- 거리
- 시간
- 코스(지도/지리)
- GPS 궤적

수동 입력의 필수 항목은 거리와 시간이다.
자동 기록은 가능한 많은 센서 데이터를 수집하고, 거리/페이스는 **기기 센서 우선 + 서버 보정** 원칙으로 처리한다.

워치는 런닝 기록에서도 입력 단말이 아니라 리모컨이다.
- 워치에서는 거리/시간 수동 입력을 받지 않는다.
- 워치에서는 시작 / 일시정지 / 재개 / 종료만 제공한다.
- 진행 중에는 현재 페이스, 거리, 누적 시간 같은 최소 상태만 보여준다.

## 5.2 신체 변화 기록

신체 기록은 장기적인 추천 시스템의 기초 데이터가 된다.

저장 항목 예시:
- 키
- 몸무게
- 체지방률
- 골격근량
- 내장지방
- 인바디 측정일
- 메모

운영 규칙 예시:
- 같은 날 여러 번 입력할 경우 덮어쓰기 전 사용자 확인을 받는다.
- 사용자는 본인의 신체 정보를 수정할 수 있다.

활용 목적:
- 체형 변화 추적
- 운동 추천 시스템 데이터 축적
- 사용자 목표 관리

## 5.3 경쟁 기능

경쟁은 현재는 **런닝 중심** 으로 설계하고, 구조는 다른 운동 카테고리로 확장 가능하게 만든다.

### 경쟁방 목록
- 현재 진행 중인 경쟁방 리스트 표시
- 검색/필터 가능
- 초대 입장 가능
- 비밀번호가 있는 비밀방 입장 가능
- 사용자는 직접 방 생성 가능
- 방 제목은 목록에서 바로 보이도록 한다.
- 경쟁방 목록은 **채팅방 목록처럼 스캔 가능한 리스트 UI** 를 권장한다.

### 경쟁방 생성 항목
- 방 제목
- 목표 거리
- 최대 인원수
- 결과 합의 여부
- 마감 시간
- 비밀방 여부 및 비밀번호
- 누적 무료 일시정지 시간(0초~300초, 최대 5분)

### 경쟁 진행 규칙
- 입장 후 대기실에서 참가자 준비 상태를 확인
- 방장이 모든 참가자 준비를 확인해야 시작 가능
- 시작 후 사용자는 다른 경쟁에 참가할 수 없음
- 진행 중 경쟁이 있으면 경쟁방 목록이 아닌 **현재 진행 중인 경쟁 화면** 으로 진입
- 경쟁 기록은 **마감 시간 내** 에만 제출 가능하다
- 마감 시간 이후 업로드/동기화된 기록은 반영하지 않는다
- 참가자는 같은 경쟁방에 속해 있더라도 **서로 다른 시각에 기록을 시작**할 수 있다
  - 여기서의 "중간 합류"는 방 입장 후 늦게 시작하는 경우를 의미한다
  - 마감 시간 내 시작만 가능하며, 마감 후 신규 시작은 불가하다
- 일시정지는 허용하되, 누적 무료 일시정지 시간을 방장 초기 설정값으로 사용한다
- 누적 무료 일시정지 시간은 여러 번 쪼개서 사용할 수 있다
- 누적 무료 일시정지 시간을 초과한 pause 시간은 1:1로 패널티가 반영된다
- 2배 패널티는 사용하지 않는다
- 일시정지 무효 판정의 세부 기준은 MVP 초안으로 두고, 운영 중 데이터와 사용성을 보면서 확정한다
- 일시정지 중 이동량이 기준치를 넘으면 해당 일시정지는 무효로 판단하고 자동 해제한다
- 무효 처리 시 사용자에게 "일시정지가 해제되었습니다" 또는 "이동이 감지되어 일시정지가 무효 처리되었습니다" 같은 경고를 보여준다
- 무효 처리된 구간은 pause 시간에 포함하지 않는다

### 경쟁 화면 원칙
- 워치에서는 경쟁 기록을 직접 입력하지 않는다.
- 워치의 역할은 현재 경쟁방 상태가 맞는지 확인하고, 시작/일시정지/재개/종료를 조작하는 최소 리모컨이다.
- 진행 중 화면은 현재 상태를 모니터링하는 화면이어야 한다.
- 워치에서는 현재 거리, 현재 페이스, 1등과의 차이, 바로 앞 사람과의 차이, ETA 같은 최소 정보만 보여준다.

### 경쟁방 비밀번호 입력/검증
- 별도의 `초대방` 타입은 두지 않고, 모든 경쟁방은 동일한 구조를 사용한다.
- 방장은 경쟁방 생성 시 비밀번호 텍스트를 직접 입력할 수 있다.
- 입장 시 사용자가 입력한 비밀번호 문자열이 저장된 문자열과 **완전히 일치해야만** 입장할 수 있다.
- 비밀번호는 개인정보가 아니므로, 현재 정책에서는 해시/암호화 요구를 두지 않는다.
- 비밀번호 검증은 단순 문자열 비교로 처리한다.
- 경쟁방에는 특정 사용자를 초대하는 기능만 별도로 제공한다.
- 초대는 방 타입이나 접근 권한 자체를 바꾸지 않으며, 특정 사용자에게 입장을 알리는 알림 기능이다.
- 초대받은 사용자는 초대 알림을 직접 탭해서 입장 흐름을 시작한다.
- 초대받은 사용자도 비공개 방이라면, 사전에 알고 있는 동일한 비밀번호를 입력해야 한다.
- 공개형 경쟁방은 비밀번호 없이 입장할 수 있다.

### 경쟁 화면
- 시작된 경쟁 화면은 **런닝 기록 화면과 유사한 구조** 를 사용한다.
- 여기에 **실시간 랭킹** 과 **현재 순위 차이** 를 함께 노출한다.
- 보여줘야 할 핵심 정보는 현재 거리, 현재 페이스, 1등과의 차이, 바로 앞 사람과의 차이, ETA 이다.
- 경쟁 중에는 준비완료 / 대기 화면과 구분되는 별도 상태를 둔다.
- 경쟁 진행 중인 사용자는 다른 경쟁방에 참가할 수 없다.

### 경쟁 시작 흐름 다이어그램 문장
- `경쟁 없음` → `Competition` 탭 진입 → `경쟁방 목록` 표시.
- `진행 중인 경쟁 있음` → `Competition` 탭 진입 → `현재 진행 중인 경쟁 화면`으로 즉시 이동.
- `현재 진행 중인 경쟁 화면` → 방 상태는 `starting_ready`.
- `starting_ready` → 사용자가 `측정 시작`을 누름 → 해당 참가자 상태는 `measuring`.
- `measuring` → 기록 종료 → 해당 참가자 상태는 `measured`.
- `모든 참가자 = measured` → 방 상태는 `finished`.
- `방장 시작` 또는 `자동 시작 조건 충족` → 방 상태는 `starting_ready`.
- `마감 1시간 전까지 시작되지 않음` → 방 상태는 `cancelled`.
- `경쟁 진행 중인 참가자` → 해당 경쟁이 종료될 때까지 다른 경쟁방에 참가할 수 없다.

### 경쟁 상태
경쟁 상태는 **방 상태(room state)** 와 **참가자 상태(participant state)** 를 분리해서 관리한다.

#### 방 상태
- `waiting_room`: 대기실 / 입장 완료
- `starting_ready`: 경쟁 시작(준비)
- `starting_measuring`: 경쟁 시작(기록 측정중)
- `starting_completed`: 경쟁 시작(기록 측정 완료)
- `running`: 경쟁 진행 중
- `finished`: 모든 참가자 측정 완료 후 종료
- `cancelled`: 시작되지 못하고 취소됨

#### 참가자 상태
- `not_joined`: 방에 없음
- `joined_ready`: 입장 완료 / 준비 완료
- `measuring`: 기록 측정중
- `measured`: 기록 측정 완료
- `running`: 진행 중
- `paused`: 일시정지 중
- `finished`: 종료 완료
- `expired`: 마감 시점까지 기록 없음
- `dnf`: 중도 포기 또는 무효
- `disqualified`: 부정행위 또는 비정상 기록
- `sync_pending`: 오프라인 기록 동기화 대기

#### 상태 운영 원칙
- 대기실에 입장하면 별도 준비 버튼 없이 바로 `joined_ready` 로 본다.
- 최대 인원이 모두 차면 방은 자동으로 시작 상태로 이동한다.
- 최대 인원이 차지 않았더라도 방장은 현재 참가 인원 기준으로 시작할 수 있다.
- `starting_ready` 는 **방 상태** 이고, `measuring` / `measured` 는 **참가자 상태** 이다.
- `starting_ready` 는 방장이 시작 버튼을 누르거나 자동 시작 조건이 충족된 직후의 상태다.
- 각 참가자는 자신의 기록을 실제로 시작할 때 `measuring` 상태로 전환된다.
- 각 참가자는 기록을 끝낼 때 `measured` 상태로 전환된다.
- 모든 참가자가 `measured` 가 되면 방은 `finished` 로 종료된다.
- 마감 1시간 전까지도 방이 시작되지 않으면 `cancelled` 로 전환할 수 있다.

### 실시간 랭킹 규칙
랭킹은 단순 기록 순이 아니라, **현재 시점의 진행률과 시간** 을 함께 반영한다.

#### 실시간 랭킹의 목적
- 진행 중인 경쟁 상황을 즉시 보여준다
- 늦게 시작한 사람도 마지막에 역전 가능하다
- 혼자 기록 중일 때도 랭킹 UI를 자연스럽게 보여준다
- 이미 기록을 남긴 사람, 진행 중인 사람, 아직 시작하지 않은 사람이 한 화면에 함께 보여질 수 있다

#### 실시간 랭킹 계산 원칙
- 1차 기준: 목표 대비 진행률
- 2차 기준: 현재 유효 운동 시간
- 3차 기준: 평균 페이스
- 4차 기준: 시작 시각
- 5차 기준: 서버 수신 시각

실시간 화면에서는 1등과의 차이, 바로 앞 사람과의 차이, 예상 완주 시각을 빠르게 확인할 수 있어야 한다.

#### 최종 랭킹 계산 원칙
- 최종 랭킹은 마감 시간 기준으로 확정한다
- 최종 랭킹은 진행 중 데이터가 아닌, 마감 시점까지 유효하게 확정된 기록만 사용한다
- `finished` 상태는 최종 기록으로 고정한다
- `running` 상태는 마감 시점 스냅샷으로 종료 처리한다
- `expired`, `dnf`, `disqualified` 는 별도 상태로 구분하여 최종 순위에 반영한다

#### 동점 처리
- 진행률이 같으면 평균 페이스가 더 좋은 사용자를 우선한다
- 평균 페이스가 같으면 유효 운동 시간이 더 짧은 사용자를 우선한다
- 그것도 같으면 시작 시각이 더 이른 사용자를 우선한다
- 그래도 같으면 공동 순위 또는 동일 순위 처리를 허용한다

#### 패널티 처리
- 일시정지 누적 시간이 방장이 설정한 누적 무료 시간을 초과하면 초과분만 패널티 점수를 부여한다
- 패널티는 랭킹에 직접 반영될 수 있으며, 최종 점수 산정 규칙과 분리해 저장한다
- 패널티 발생 시 UI에 명확히 표시한다

### 경쟁 시나리오
아래 시나리오를 모두 지원해야 한다.
- 모두가 동시에 실시간으로 경쟁하는 경우
- 일부만 경쟁 중이고 일부는 아직 시작하지 않은 경우
- 일부는 이미 기록을 남겼고 후발자가 경쟁을 시작하는 경우
- 일부는 이미 기록을 남겼고 일부는 경쟁 중이며 일부는 아직 시작하지 않은 경우
- 일부는 이미 경쟁을 끝냈고 일부는 아직 시작하지 않은 경우
- 아무도 아직 기록을 남기지 않은 경우
- 일부는 일시정지 상태인 경우
- 일부는 오프라인 동기화 대기 상태인 경우
- 일부는 DNF 또는 무효 처리된 경우
- 일부는 부정행위 판정으로 제외된 경우

### 경쟁 취소 메시지
- 경쟁이 시작되지 못하고 취소될 때는 경기장 분위기에 맞는 안내 문구를 사용한다.
- 권장 문구 예시: **"오늘의 경기는 성사되지 않았습니다. 콜로세움의 문을 닫습니다."**
- 더 짧은 대안: **"오늘의 경기는 성사되지 않았습니다."**
- 너무 현대적인 표현보다, 경기 종료/성사 실패 느낌이 나는 문구가 적합하다.

### 경쟁 결과 합의
- 결과 합의는 동의/비동의만 기록한다.
- 전원 동의 여부는 별도 표시가 가능하도록 한다.
- 합의 데이터는 추후 내기 기능 확장의 근거 데이터로 사용할 수 있다.

### 종료 및 결과
- 마감 시간까지 기록이 없으면 빈 점수 처리
- 경쟁 종료 후 순위 표시
- 결과는 개인 활동 기록에 저장
- 결과 합의에 대한 투표를 진행
- 동의/비동의 기록 저장
- 최종 종료 후에는 실시간 랭킹과 별도로 **최종 랭킹** 이 저장된다

## 8. 환경 설정 정책

요구사항에 맞춰 환경 파일은 다음처럼 운영한다.

- `.env` : **포맷/예시용**. 필요한 키 이름과 기본 설명을 담는다.
- `.env.local` : 로컬 개발 전용. 저장소에 커밋하지 않는다.
- `.env.prod` : 운영 환경 전용. 저장소에 커밋하지 않는다.

추가 정책:
- `.env.local`, `.env.prod` 는 권한이 제한된 배포/운영 절차에서만 사용한다.
- 개발자는 `.env` 샘플을 보고 필요한 값을 준비한다.
- 실제 비밀값은 Secret Manager 또는 배포 환경 변수로 주입한다.
- Git에는 민감정보가 절대 들어가지 않도록 한다.

권장 파일 예시:
- `.env.example` 또는 `.env` 샘플에 필요한 변수 목록을 문서화
- `.env.local`, `.env.prod` 는 `.gitignore` 대상 유지

## 9. API 설계 방향

### 인증
- OAuth2 소셜 로그인
- 사용자 식별은 내부 `user_id` 로 관리
- 디바이스별 토큰 등록 지원

### 실시간 기능
- 경쟁방 상태, 랭킹, 채팅은 WebSocket 또는 SSE 고려
- 모바일/워치 연결 상태를 고려해 재연결 로직 필요

### 지도/경로
- 런닝 코스는 GPS 트랙과 지도 렌더링을 분리
- 지도 SDK는 플랫폼별 네이티브 SDK를 우선 고려

### 채팅
- 기본 DM부터 시작
- 후에 그룹 채팅/알림 채널로 확장 가능
- 비동기 전송이 필요하면 큐/브로커 도입

## 13. 결론

PPOLO는 **운동 기록 + 실시간 경쟁 + 소셜** 을 하나로 묶는 서비스다.
초기에는 **Go 기반 모듈러 모놀리스** 로 빠르게 출시하고, 데이터와 트래픽이 쌓이면 경쟁/채팅/알림을 분리하는 방향이 가장 현실적이다.

핵심은 다음 세 가지다.
- 운동 기록의 정확성
- 경쟁의 실시간성
- 확장 가능한 도메인 구조
