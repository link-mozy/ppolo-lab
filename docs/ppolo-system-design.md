# PPOLO 시스템 설계서

> 서비스명: **PPOLO**  
> 목적: 운동 기록과 경쟁을 결합해 운동을 더 재미있게 만드는 **기록 + 소셜 네트워크 서비스**

---

## 1. 서비스 개요

PPOLO는 사용자의 운동 활동과 신체 변화를 기록하고, 다른 사용자와 실시간 경쟁을 통해 운동의 동기부여를 높이는 서비스다.

핵심 사용 맥락은 다음과 같다.
- **모바일 앱**: 운동 기록, 대결 참여/생성, 소셜, 캘린더, 신체 정보 관리
- **스마트 워치 앱**: 활동 시작/중지 제어, 현재 페이스 확인, 운동 중 실시간 보조
- **백엔드 API**: 인증, 기록 저장, 경쟁방, 실시간 랭킹, 채팅, 알림, 통계
- **DB/분석**: 운동 데이터, 경쟁 결과, 인바디 변화, 추천 시스템 기반 데이터 축적

---

## 2. 제품 원칙

PPOLO는 다음 원칙으로 설계한다.

- **기록의 정확성**: 운동/대결 데이터는 사용자의 실제 행위와 기기 센서 데이터를 함께 저장한다.
- **실시간성**: 경쟁은 현재 시점의 거리/시간/페이스를 반영해 실시간 순위를 보여준다.
- **확장성**: 초기에는 런닝/헬스 중심으로 시작하고, 추후 다른 운동 카테고리를 추가한다.
- **플랫폼 분리**: 모바일 앱과 스마트 워치 앱은 별도 클라이언트로 분리한다.
- **도메인 분리**: 백엔드는 기능별 경계를 명확히 하고, 나중에 서비스 분리가 가능하도록 설계한다.

## 3. 추천 아키텍처

## 3.1 백엔드 아키텍처: 모듈러 모놀리스 우선, MSA는 단계적 도입

초기에는 **모듈러 모놀리스(modular monolith)** 를 추천한다.

이유:
- 서비스 초기에는 기능이 많아 보여도 실제 트래픽/조직 규모는 아직 작다.
- 활동 기록, 경쟁, 채팅, 알림은 서로 긴밀히 연결돼 있어 초기부터 완전한 MSA로 나누면 운영 복잡도만 커진다.
- Go는 패키지 경계와 인터페이스 분리가 명확해서 모듈러 모놀리스에 잘 맞는다.

다만, 다음 조건이 충족되면 특정 도메인부터 MSA로 분리한다.
- 팀이 기능별로 분업되기 시작할 때
- 경쟁/채팅/알림 트래픽이 급증할 때
- 실시간 처리와 배치 처리의 성격이 완전히 갈라질 때
- 독립 배포가 필요한 기능이 생길 때

### 권장 도메인 경계

- **Auth / Identity**: OAuth2 소셜 로그인, 세션/토큰, 디바이스 등록
- **User / Profile**: 사용자 기본 정보, 프로필, 공개 범위, 팔로우/차단
- **Health / Body Metrics**: 키, 몸무게, 체지방, 골격근량, 인바디 기록
- **Activity Log**: 헬스/런닝 기록, 센서 데이터, 운동 이력
- **Competition**: 경쟁방 생성/입장/진행/종료/투표
- **Ranking / Realtime**: 실시간 순위 계산, 현재 페이스/진행률 계산
- **Social / Chat**: DM, 채팅방, 메시지 송수신
- **Calendar**: 기록/대결 일정 조회
- **Notification**: 푸시, 인앱 알림, 이벤트 알림
- **Analytics / Recommendation**: 추천 데이터, 집계, 통계
- **Admin / Ops**: 운영자 기능, 신고, 제재, 이벤트 관리

## 4. 추천 기술 스택

## 4.1 API 서버

백엔드는 **Go** 로 구현한다.

권장 구성:
- **언어**: Go
- **HTTP Router**: `chi` 또는 `gin`
- **DB**: PostgreSQL
- **캐시 / PubSub**: Redis
- **실시간 이벤트**: WebSocket + Redis Pub/Sub 또는 NATS
- **비동기 작업**: Background worker / queue
- **ORM/SQL 계층**: `sqlc` + `pgx` 조합 권장
- **마이그레이션**: goose / golang-migrate
- **인증**: OAuth2 소셜 로그인 + JWT 또는 세션 토큰
- **관측성**: OpenTelemetry + 구조화 로그 + 메트릭

### MSA 추천 여부

- **초기 권장**: MSA 아님
- **권장 형태**: 모듈러 모놀리스 + 필요 시 워커 분리
- **향후 분리 후보**: 채팅, 알림, 추천/분석, 실시간 랭킹 보조 서비스

---

## 4.2 모바일 앱

요구사항상 **모바일 네이티브 앱** 으로 설계한다.

권장 방향:
- iOS: Swift + SwiftUI
- Android: Kotlin + Jetpack Compose

운영 전략은 두 가지다.
1. **양 플랫폼 동시 네이티브 개발**: UX 일관성이 높고 센서/헬스 연동에 유리
2. **MVP 우선 1개 플랫폼 출시 후 확장**: 초기 속도를 높일 수 있음

PPOLO는 헬스/런닝/워치 연동이 중요하므로, 장기적으로는 네이티브 분리가 적합하다.

---

## 4.3 스마트 워치 앱

스마트 워치는 모바일 앱의 보조 인터페이스가 아니라 **독립 클라이언트** 로 본다.

권장 방향:
- iPhone 연동: watchOS
- Android 연동: Wear OS

워치의 역할:
- 운동 시작 / 일시정지 / 종료
- 현재 페이스 확인
- 최소한의 운동 상태 피드백
- 센서 데이터 수집 동의 시 심박수/활동 데이터 전송

워치 UI는 정보 과부하를 피하고 1~2개의 핵심 숫자만 노출한다.

## 5. 기능 설계

## 5.1 운동 활동 기록

### 지원 우선순위
- 1차: **헬스, 런닝**
- 2차: 요가, 자전거, 필라테스, 크로스핏, 하이록스

### 헬스 기록
사용자가 모바일 앱에서 수동 입력한다.
- 운동 부위
- 운동 종목
- 무게
- 횟수
- 세트 수
- 운동 시간
- 메모

워치 연동 시 추가 저장 가능:
- 운동 시작 시각
- 심박수
- 활동 중 심박 변화

### 런닝 기록
런닝은 시작/중지 기반 활동 기록으로 설계한다.
- 시작
- 일시정지
- 재개
- 종료

기록 항목:
- 심박수
- 케이던스
- 페이스
- 거리
- 시간
- 코스(지도/지리)
- GPS 궤적

워치에서는 다음만 최소 노출한다.
- 현재 페이스
- 일시정지/재개/종료 버튼

## 5.2 신체 변화 기록

신체 기록은 장기적인 추천 시스템의 기초 데이터가 된다.

저장 항목 예시:
- 키
- 몸무게
- 체지방률
- 골격근량
- 내장지방
- 인바디 측정일
- 메모

활용 목적:
- 체형 변화 추적
- 운동 추천 시스템 데이터 축적
- 사용자 목표 관리

---

## 5.3 경쟁 기능

경쟁은 현재는 **런닝 중심** 으로 설계하고, 구조는 다른 운동 카테고리로 확장 가능하게 만든다.

### 경쟁방 목록
- 현재 진행 중인 경쟁방 리스트 표시
- 검색/필터 가능
- 초대 입장 가능
- 비밀번호가 있는 비밀방 입장 가능
- 사용자는 직접 방 생성 가능

### 경쟁방 생성 항목
- 방 제목
- 목표 키로수
- 최대 인원수
- 결과 합의 여부
- 마감 시간
- 비밀방 여부 및 비밀번호

### 경쟁 진행 규칙
- 입장 후 대기실에서 참가자 준비 상태를 확인
- 방장이 모든 참가자 준비를 확인해야 시작 가능
- 시작 후 사용자는 다른 경쟁에 참가할 수 없음
- 진행 중 경쟁이 있으면 경쟁방 목록이 아닌 **현재 진행 중인 경쟁 화면** 으로 진입

### 실시간 랭킹 규칙
랭킹은 단순 기록 순이 아니라, **현재 시점의 진행률과 시간** 을 함께 반영한다.

권장 계산 방식:
- 1차 기준: 목표 대비 진행률
- 2차 기준: 경과 시간
- 3차 기준: 평균 페이스

이 방식의 장점:
- 늦게 시작해도 역전 가능
- 실시간 경쟁 재미를 유지
- 혼자 기록 중일 때도 랭킹 UI를 자연스럽게 보여줄 수 있음

### 종료 및 결과
- 마감 시간까지 기록이 없으면 빈 점수 처리
- 경쟁 종료 후 순위 표시
- 결과는 개인 활동 기록에 저장
- 결과 합의에 대한 투표를 진행
- 동의/비동의 기록 저장

## 7. 로그 및 모니터링 설계

## 7.1 로그 포맷

운영과 추적을 위해 **구조화 JSON 로그** 를 기본으로 사용한다.

필수 필드 예시:
- `timestamp`
- `level`
- `service`
- `environment`
- `version`
- `build_sha`
- `trace_id`
- `request_id`
- `user_id`
- `device_id`
- `device_type`
- `platform`
- `route`
- `method`
- `status_code`
- `latency_ms`
- `competition_id`
- `activity_session_id`
- `room_id`
- `error_code`
- `error_message`
- `ip`
- `user_agent`

### 로그 설계 원칙
- 사람이 읽기 쉬워야 한다
- 검색/필터링이 쉬워야 한다
- 장애 분석에 필요한 추적 ID가 항상 포함돼야 한다
- 민감 정보는 로그에 남기지 않는다

### 권장 모니터링 구성
- 애플리케이션 로그: stdout JSON
- 메트릭: Prometheus
- 대시보드: Grafana
- 분산 추적: OpenTelemetry + Tempo/Jaeger
- 중앙 로그: Loki / Elasticsearch / Cloud logging

## 8. 환경 설정 정책

요구사항에 맞춰 환경 파일은 다음처럼 운영한다.

- `.env` : **포맷/예시용**. 필요한 키 이름과 기본 설명을 담는다.
- `.env.local` : 로컬 개발 전용. 저장소에 커밋하지 않는다.
- `.env.prod` : 운영 환경 전용. 저장소에 커밋하지 않는다.

추가 정책:
- `.env.local`, `.env.prod` 는 권한이 제한된 배포/운영 절차에서만 사용한다.
- 개발자는 `.env` 샘플을 보고 필요한 값을 준비한다.
- 실제 비밀값은 Secret Manager 또는 배포 환경 변수로 주입한다.
- Git에는 민감정보가 절대 들어가지 않도록 한다.

권장 파일 예시:
- `.env.example` 또는 `.env` 샘플에 필요한 변수 목록을 문서화
- `.env.local`, `.env.prod` 는 `.gitignore` 대상 유지

## 9. API 설계 방향

### 인증
- OAuth2 소셜 로그인
- 사용자 식별은 내부 `user_id` 로 관리
- 디바이스별 토큰 등록 지원

### 실시간 기능
- 경쟁방 상태, 랭킹, 채팅은 WebSocket 또는 SSE 고려
- 모바일/워치 연결 상태를 고려해 재연결 로직 필요

### 지도/경로
- 런닝 코스는 GPS 트랙과 지도 렌더링을 분리
- 지도 SDK는 플랫폼별 네이티브 SDK를 우선 고려

### 채팅
- 기본 DM부터 시작
- 후에 그룹 채팅/알림 채널로 확장 가능
- 비동기 전송이 필요하면 큐/브로커 도입

## 10. 서비스 운영/확장 전략

### MVP 우선순위
1. 회원가입/로그인
2. 헬스 기록
3. 런닝 기록
4. 경쟁방 생성/참여
5. 실시간 랭킹
6. 신체 변화 기록
7. 알림/채팅
8. 추천 시스템

### 확장 전략
- 초기에는 런닝/헬스만 집중
- 다른 운동 카테고리는 도메인 확장으로 추가
- 추천 시스템은 데이터가 쌓인 뒤 도입
- 채팅은 별도 서비스로 분리 가능하도록 이벤트 기반 인터페이스를 유지

현재 저장소는 설계 중심으로 시작하고, 이후 아래 구조로 확장하는 것을 추천한다.

## 12. 결정이 필요한 초기 질문

실제 구현 전에 아래 항목을 먼저 확정하면 좋다.

- 모바일 MVP를 iOS부터 시작할지, Android부터 시작할지, 또는 양 플랫폼 동시인지
- 워치를 Apple Watch 중심으로 갈지, Wear OS 중심으로 갈지
- 경쟁 순위의 1차 기준을 "진행률" 중심으로 둘지, "기록 시간" 중심으로 둘지
- 채팅을 MVP에 포함할지, 2차 릴리즈로 미룰지
- 추천 시스템을 로그 적재 단계부터 넣을지

## 13. 결론

PPOLO는 **운동 기록 + 실시간 경쟁 + 소셜** 을 하나로 묶는 서비스다.
초기에는 **Go 기반 모듈러 모놀리스** 로 빠르게 출시하고, 데이터와 트래픽이 쌓이면 경쟁/채팅/알림을 분리하는 방향이 가장 현실적이다.

핵심은 다음 세 가지다.
- 운동 기록의 정확성
- 경쟁의 실시간성
- 확장 가능한 도메인 구조
